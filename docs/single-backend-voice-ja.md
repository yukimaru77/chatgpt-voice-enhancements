# Codex app Voice：既存バックエンドへの集約と、省略しない音声伝達

## 1. 何をしたいか

★ ユーザーの希望は、音声モデルを「もう一人の回答者」にせず、既存の Codex を回答と作業の唯一の担当にすることです。

- ② 音声モデルが単独で行うのは、挨拶・相づち・短い受領の返事など、実質的な情報や判断を含まない受け答えだけ。
- 質問への回答、説明、相談、計算、調査、計画、実装、操作などは、簡単なものも含めてすべて①へ渡す。迷った場合も①へ渡す。
- ① 元の Codex が、元のセッションを維持したまま、同じスレッド内で回答・作業・検証を行う。別タスクやサブエージェントに委譲しない。
- ②は①の回答を要約・省略しない。情報、順序、数値、条件、否定、留保、ニュアンスを維持し、自然に話せるよう必要最小限の言い回しだけ変える。独自の説明や結論を足さない。

実際に適用するプロンプトは **英語**。この日本語文書はユーザーが読んで確認するための説明です。英語の指示を使っても、発話言語はユーザーの言語に合わせます。

| アプリ同梱 Codex | `0.154.0-alpha.6.2` |

| 調査した主要アセット | `app-initial-9b95fa538c62.js`、`avatar-overlay-native-page-bb89afb2a8f6.js` |

根拠はインストール済みアプリの `Info.plist`、同梱実行ファイル、`app.asar` の実装と、実際の音声テストのログです。上記の圧縮後の識別子はこのビルドを説明するためのものです。

### 登場する役割

| 役割 | セッションと仕事 |
| --- | --- |
| ★ ① 元の Codex／バックエンド | 既存のスレッド ID を引き継ぐ。元の履歴、作業の文脈、モデル設定などを持つ。ツールを使って作業できる。 |
| ② リアルタイム音声モデル | Voice 開始時に接続される別の会話コンテキスト。音声を理解し、話す。単なる TTS ではなく、自分で回答する能力もあるため、その裁量を今回の指示で絞る。 |
| ③ 別の作業タスク | 必須の中継役ではない。①が別タスクを作って仕事を委譲する場合の任意の経路。今回の方針では使わない。 |

既存タスクからの開始は `composer_button_existing_thread` → `exact` の経路を使い、同じ `threadId` で `thread/realtime/start` を呼びます。Voice のために元のセッションを作り直す必要はありません。

②に元のセッション全体がそのまま渡るわけではありません。②には基本プロンプト、設定に応じた直近のタスク履歴・過去の音声会話・メモリ等が渡ります。①は元のタスクを保持し、②からの引き継ぎを受けて動きます。今回、履歴の件数やコンテキスト上限は変えていません。

典型的な往復は次のとおりです。

```text
ユーザーの音声
  → ② 音声モデル
  → 引き継ぎ（ユーザーの発言と、直近の会話追加分）
  → ① 元の Codex：同じスレッドで回答・ツール実行
  → ①の進捗・回答
  → ②：音声で伝える
```

①のログでは引き継ぎが `<realtime_delegation>` 内の `<input>` と `<transcript_delta>` として現れます。これは毎回セッション開始以来の全履歴を渡す、という意味ではありません。

このビルドにはアプリが通話を所有する経路と、バックエンド側が所有する経路があります。前者では音声モデル向けの `instructions`、後者では開始要求の `prompt` に基本プロンプトが渡ります。今回の差し替え箇所は、この分岐より前です。

新規 Voice 用の既定指示には、会話を止める長い仕事を別のワーカー Codex タスクに委譲する方針が含まれます。音声モデルの既定指示にも、短くまとめて伝える方針があります。今回の希望とは競合するので、単に末尾へ一文足すのではなく、該当する Voice 用指示を差し替えています。

## 3. なので、どう変えたか

### ★ ①・②への英語プロンプトを、実際の開始引数で差し替える

| ファイル | 適用先 | 内容 |
| --- | --- | --- |
| [frontend.md](../voice-policy/frontend.md) | ②向け `prompt` | 受け答え以外をバックエンドへ渡す。返答の要約・省略・独自の補足をしない。 |
| [backend.md](../voice-policy/backend.md) | ①向け `realtimeStartInstructions` | 全回答・全作業を同じスレッドで行う。別タスク・サブエージェントへ委譲しない。既存の履歴と権限を保持する。 |
| [end.md](../voice-policy/end.md) | `realtimeEndInstructions` | Voice 固有の役割分担と出力プロトコルを終了し、通常のタスク動作へ戻す。 |

開始直前の引数を差し替えるため、配信設定による文面や条件付きの計画用追記が、古い方針のまま残るのを避けられます。Voice の出力タグとインライン表示方法、画面取得・通話終了の扱いは新しい指示にも残しています。

新規 Voice タスクには、別ワーカーへ委譲する既定の開発者指示の代わりに、同じスレッドで作業する短い英語の指示を渡します。新規タスクに渡す動的ツール設定では `transferVoiceCallEnabled` を `false` にします。既存タスクに登録済みのツールを削除する処理ではありません。

### アップデートに対する備え

- 関数名、変数名、アセットのハッシュを固定しない。Voice 開始の `prompt`、`realtimeStartInstructions`、`realtimeEndInstructions` などのプロパティ名から、そのビルドの引数を特定する。
- コーディネーターの検出もプロパティ名を使う。引数の並べ替え、圧縮による変数名の変更、単純な追加フィールドに対応する。
- 対象がゼロ件または複数件ならインストールを失敗させる。未知の構造で「適用済み」とは報告しない。
- 起動前にローカルの `app.asar` を読み取り専用で調べる `--check-app-compatibility` を追加。通常のインストーラーも、新方針が有効なら起動・再起動の前にこの互換性を検査する。
- 指示文と実装ファイルの内容をハッシュ化し、再インストール時に古いヘルパーを誤って再利用しない。
- 音声ウィンドウを実行前に停止させるとデバッガー初期化自体が詰まるケースに対処し、新しいウィンドウを停止させない方式に変更。新方針のインストールでは、メイン画面と音声画面の両方の設定完了を待ち、エラーを成功扱いにしない。Voice はインストール成功を確認してから開始する。

これは「将来どの変更にも壊れない」という保証ではありません。プロパティ名や開始方式そのものが変わった場合は、明示的に非互換として停止し、新しい実装を確認する必要があります。

### 変更しないものと、保証の境界

★ この実装はプロンプト方針であり、ツール権限のサンドボックスではありません。①に別スレッドを使わないよう明示し、新規 Voice 用の転送フラグも無効にしますが、既存タスクの CLI サブエージェント機能や、すべての迂回経路を強制遮断するものではありません。

「単純な受け答え」の判定と、省略しない言い換えはモデルが行うため、任意の会話における完全遵守を保証するものではありません。実機テストでは、具体的な回答について内容が保たれたことを比較検証します。

アプリの署名済みファイル、ユーザーのグローバル設定、選択モデル、推論強度、元のスレッド ID、履歴量、通常のテキスト入力やディクテーションは変更しません。パッチはメモリ内に適用し、アプリの終了で消えます。

新しい指示が有効になるのは次の Voice 開始時です。インストーラーを再実行しただけで、進行中の音声セッションのプロンプトが置き換わるわけではありません。

## 4. 使い方と戻し方

既定値は `single-backend` です。

```bash
node inject-chatgpt-voice-enhancements.mjs 9229 30000 --check-app-compatibility
./install-chatgpt-voice-enhancements.sh
node diagnose-chatgpt-voice-enhancements.mjs 9229 --assert-voice-policy
```

アプリがデバッガーなしで起動している場合は、インストーラーの `--restart` で必要な再起動を許可できます。アプリ更新後も、同じ手順で互換性確認と再適用を行います。

プロンプトを変えるときは `voice-policy/` 内の英語ファイルを編集し、再インストールして Voice を開始し直します。

この新しい指示の差し替えを止め、アプリ既定の指示へ戻す場合：

```bash
CHATGPT_VOICE_POLICY=native ./install-chatgpt-voice-enhancements.sh
```

これは既存の Voice 解放・マイク処理・表示の改造は維持し、今回の新しい指示差し替えを無効にする設定です。終了済み・過去のスレッドに保存された履歴や、新規 Voice タスクに既に渡した開発者指示を消す機能ではありません。

## 5. 検証

```bash
node --test voice-policy.test.mjs
node inject-chatgpt-voice-enhancements.mjs 9229 30000 --self-test
node inject-chatgpt-voice-enhancements.mjs 9229 30000 --check-app-compatibility
```

自動テストでは、引数名・順番の変化、未知・重複した対象の拒否、3本の指示の差し替え、元のスレッド・ホスト・マイク・モデル等の保持、元設定オブジェクトを直接変更しないこと、既定動作へ戻す設定を確認します。

### 実際のアプリに音声を入力するテスト

テスト用の既存セッションに `QUARTZ-318` という確認コードを記憶させてから、同じスレッドで Voice を開始しました。音声で、準備したファイルの内容、元の確認コード、十七かける二十三の結果を尋ねました。

この Mac には入力用マイクが認識されていないため、macOS の音声合成で作った 48 kHz・モノラル WAV を、アプリの音声用 `getUserMedia` に一時的に接続しました。そこから先は実際の音声処理、WebRTC、リアルタイムモデル、バックエンドへの引き継ぎを通しています。テキスト入力を音声テストの代わりに使っていません。

確認項目は、音声の文字起こし、同じスレッドへの引き継ぎ、①による `tests/voice-facts.txt` の読み取り、元の確認コードの保持、別スレッド作成なし、①の最終回答と②の最終発話の内容一致、音声の送受信、通話終了です。結果の抜粋と判定は [実音声テストの記録](voice-policy-smoke-2026-09-13.json) に保存しました。

★ 通常起動時と、アプリを完全終了してからの再起動後の **2 回とも成功**しました。どちらも同じ元スレッドでファイルを読み、確認コード `QUARTZ-318` と計算結果 `391` を保持しました。別ワーカーへのツール呼び出しはありませんでした。

1 回目は制御タグと空白を除くと最終回答と発話テキストが完全一致。2 回目の差は「木曜日の午前十時」→「木曜日午前十時」の助詞 1 文字のみでした。数値、雨天時の条件、保険料の除外、到着日の不確実性を含め、回答の情報と順序は維持されています。

発話内容の比較にはアプリが出す音声応答のトランスクリプトを使い、WebRTC の送受信と正の音声エネルギーも確認しました。出力音声を別の認識器で再文字起こしした検証ではありません。

この方法は実際のモデルと通信する統合テストですが、物理マイクの動作確認ではありません。テスト後は両方の画面で音声入力の差し替えを解除し、通話を終了しました。アプリはパッチ適用済みの状態で起動したままです。

テスト補助は `tests/voice-smoke.mjs` です。これは検証用スレッドを明示して実行するツールで、通常のインストールでは起動しません。検証用のサービス取得部分にはこのビルド用のアダプターがあり、製品用のフックとは切り離しています。
